Suggestions, the core model: a change Bridge files as a GitHub issue instead of a branch, so a design system owner needs only Issues write and a developer applies it with their own access. `composeSuggestionIssue` / `parseSuggestionIssue` write and read the issue: readable Markdown, then a collapsed JSON payload (schema `bridge.suggestion/1`) whose canonical sha256 sits in a marker, so an edit by hand is detected. Token changes are stored as edits (paths and values), other files as whole contents with git blob shas before and after; contents too large for GitHub's 65,536-character body move to up to 8 continuation comments and are reassembled (a missing part is refused). Labels (`bridge-suggestion`, `suggestion: <kind>`, `source:`, `tier:`, one state label), the status machine (`suggestionStatus`: needs review, changes requested, approved, applying, applied, declined, outdated) and path safety rules per kind (`suggestionPathProblems`: repo-relative only, inside the kind's folders, never a governance guardrail). Reviews are comments (`suggestion-review.ts`): `summarizeSuggestionApprovals` counts only the configured owners (collaborators when no owner is set) and only on the current payload sha, so an edit makes earlier approvals stale. GitHub calls in `suggestions-github.ts`: create (with parts), list, get, review, link the applying pull request, decline. Config: `changes` (`"suggest"`, the default, or `"direct"`, with `changesMode()`) and `storybook.url` (`storybookUrl()` falls back to `previews.production.storybook`). `listIssueComments` now also returns `createdAt` and `authorAssociation`.
